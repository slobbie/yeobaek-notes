# 운영 준비 검증 기록

## 현재 상태

- 검증 기준일: 2026-09-14 (Asia/Seoul)
- 검증 브랜치: `chore/production-readiness`
- 대상: 공개 웹, 로컬 관리자, 연결된 Supabase 프로젝트, 비식별 분석 수집 경계
- Q-01 결과: 자동 검증 완료, 사용자 인수 검수 대기
- 배포 차단 항목: 실제 사용자가 수행하는 관리자 작성·발행·수정 및 공개 화면 확인이 남아 있음
- 운영 데이터: 검증 데이터는 모두 삭제했으며, 운영에 사용할 글은 D-01 배포 전에 관리자가 직접 등록한다.

운영 도메인과 Vercel 프로젝트는 D-01에서 확정한다. 따라서 현재 로컬 주소로 생성되는 canonical, RSS, sitemap과 분석 함수의 허용 origin은 배포 설정값이 아니라 로컬 검증값이다.

아래 결과는 배포 승인 결과가 아니다. 저장소 검사, API 요청과 자동화된 브라우저 조작으로 확인한 기술 검증 결과이며, 실제 사용자의 인수 검수가 끝날 때까지 D-01을 시작하지 않는다.

## 자동 검증 결과

| 항목 | 결과 | 근거 |
| --- | --- | --- |
| 공개·관리자 DB 경계 | 통과 | 공개 키는 발행 글만 읽었고 글 쓰기, 관리자 저장 RPC, 분석 원본·집계 읽기와 직접 쓰기는 거부됐다. service role은 초안과 발행 글, 관리자 지표를 읽고 관리자 저장 경계를 실행했다. |

| 공개 화면과 피드 | 통과 | 홈, 주제 필터, 검색 빈 결과, 목록, 상세, 소개, 404, RSS, sitemap, robots를 확인했다. 초안은 홈·상세·RSS·sitemap에서 제외됐다. |
| 반응형 화면 | 통과 | 데스크톱 화면을 직접 확인하고 Chrome 390×844 뷰포트에서 홈·상세·소개를 확인했다. 문서 너비와 주요 콘텐츠의 `scrollWidth`가 390px 뷰포트를 넘지 않았다. |

| SEO·GEO 표면 | 통과 | 상세 제목, canonical, Open Graph, BlogPosting JSON-LD의 제목·날짜·분야·태그·출처가 공개 글과 일치했다. RSS와 sitemap에는 발행 글만 포함됐다. |

| 백업·복구·롤백 | 통과 | 원격 스키마와 데이터를 덤프하고, 초기화한 로컬 Supabase에 public 데이터 백업을 복원했다. 발행 글 1건, 초안 1건, 해당 집계 3건이 일치했다. 권한 변경 트랜잭션은 롤백 전후 실행 권한이 원상복구되는 것을 확인했다. |

검증용으로 만든 발행 글 1건, 초안 1건, 원본 분석 이벤트 3건과 일별 집계 3건은 검증 후 원격에서 삭제했다. 조회 결과 남은 검증 글과 집계는 각각 0건이다.

## 실행한 검사

```text
npm test
  49개 테스트 통과

npm run build
  Next.js 16.3.4 공개 웹 프로덕션 빌드 통과

supabase migration list
  로컬·원격 마이그레이션 4개 일치

supabase db lint --linked --level error
  오류 없음
```

HTTP 확인 결과는 홈·소개·상세·robots·sitemap·RSS가 200, 초안 상세와 존재하지 않는 경로가 404였다. 공개 키 쓰기와 비공개 데이터 접근은 401 또는 권한을 숨기는 404로 종료됐다.

## 백업과 복구 절차

1. 변경 전에 연결된 프로젝트의 스키마와 public 데이터를 각각 덤프한다.

   ```text
   supabase db dump --linked --file <schema-backup.sql>
   supabase db dump --linked --data-only --use-copy --schema public --file <public-data-backup.sql>
   ```

2. 복구 시험은 운영 DB가 아니라 격리한 로컬 Supabase에서 먼저 수행한다.

   ```text
   supabase db reset --local
   psql <supabase status로 확인한 로컬 DB URL> -v ON_ERROR_STOP=1 -f <public-data-backup.sql>
   ```

3. `posts`, `post_sources`, `analytics_events`, `analytics_daily_metrics`의 건수와 대표 행을 원본과 비교한다. 공개 키로 초안이 읽히지 않는지도 다시 확인한다.
4. 운영 복구가 필요하면 쓰기와 배포를 먼저 중지하고 새 격리 환경에서 백업을 검증한다. 전체 덮어쓰기 대신 손상된 범위를 식별해 선택 복구하고, 공개 읽기와 관리자 쓰기 검증을 마친 뒤 트래픽을 재개한다.

백업 파일은 검증 중 `/private/tmp`에만 만들었고 저장소에는 포함하지 않았다.

## 되돌리기 절차

- 공개 앱: 직전 정상 Vercel 배포로 되돌린 뒤 홈, 상세, 404, robots, sitemap, RSS와 canonical을 다시 확인한다.
- Edge Function: 직전 정상 소스로 `collect-analytics`를 재배포한다. 수집 중지가 우선이면 운영 origin을 허용 목록에서 제거하고 공개 앱의 수집 요청을 비활성화한다.
- DB: 원격에 적용한 마이그레이션 파일을 삭제하거나 이력을 되감지 않는다. 수정 내용을 새 전진 마이그레이션으로 만들고 로컬 초기화·복구 시험 후 적용한다.
- 데이터: 적용 직전 백업을 격리 환경에 먼저 복원하고, 확인된 행만 선택 복구한다. 복구 중에는 관리자 쓰기를 중지한다.

## 사용자 인수 검수

실제 사용자가 다음 흐름을 직접 완료하고 결과를 확인해야 Q-01을 최종 통과로 변경한다.

1. 로컬 관리자에서 새 글의 전체 필드를 키보드와 마우스로 입력한다.
2. 초안 저장 후 관리자 목록에서 다시 열어 입력값이 유지되는지 확인한다.
3. 초안 상태에서 공개 상세 주소가 404인지 확인한다.
4. 발행 전 검사 결과를 읽고 `발행`을 실행한다.
5. 공개 홈, 검색, 분야 필터와 상세 화면에서 발행 글이 올바르게 보이는지 확인한다.
6. 제목이나 본문을 수정하고 공개 화면에 변경이 반영되는지 확인한다. 공개 캐시는 최대 300초가 걸릴 수 있다.
7. 모바일 기기 또는 브라우저 모바일 모드에서 홈과 상세를 읽고 가로 스크롤, 잘림과 조작 불편이 없는지 확인한다.
8. 관리자 `지표` 화면에서 테스트 중 만든 조회·글 열람·출처 열람 이벤트가 집계되는지 확인한다.

검수 중 만든 글과 지표를 유지할지 삭제할지는 사용자가 결정한다. 오류가 하나라도 있으면 현상, 주소, 입력값과 화면을 기록하고 Q-01을 통과 처리하지 않는다.

## D-01에서 수동으로 확인할 항목

- 운영 도메인을 확정하고 `NEXT_PUBLIC_SITE_URL`을 정확한 HTTPS origin으로 설정한다.
- `ANALYTICS_ALLOWED_ORIGINS`에 운영 origin을 추가하고 불필요한 로컬 origin은 제거한다.
- 공개 Vercel 프로젝트에 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_SITE_URL`만 등록하고 service role 키가 없는지 확인한다.
- 비어 있지 않은 상태로 공개하려면 배포 전에 관리자가 운영 글을 직접 등록·발행한다.
- 운영 주소에서 공유 미리보기와 Search Console 소유권·sitemap 제출을 확인한다.
- 공개 데이터 캐시는 최대 300초 후 갱신된다. 즉시 반영이 필요한 운영 정책으로 바뀌면 별도 무효화 작업이 필요하다.

## 남은 비차단 항목

- 관리자 자동화 도중 출처 확인일의 브라우저 값 주입이 React 상태에 반영되지 않아, 초안 생성은 같은 관리자 저장소 경계를 직접 호출해 진행했다. 발행과 수정은 관리자 화면에서 완료했다. 실제 키보드 입력은 별도 수동 점검 대상이다.
- 출처 확인일 누락 오류 문구의 조사 표현(`날짜을`)은 기능과 데이터 경계에는 영향이 없는 문구 개선 항목이다.
